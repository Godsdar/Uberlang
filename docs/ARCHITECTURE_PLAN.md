# Lingua архитектура редизайн и деплой

> Обновление 13 октября: это исходный план, а не описание целиком реализованной системы. Текущие границы и графические взаимодействия: [ADR-011](decisions/ADR-011-progressive-language-exploration.md), [ревью](reviews/2026-10-13-architecture.md). Концепт — второй Vite entry, деплой — бесплатный Vercel + Pages; backend не добавлен.

Дополнение к техническому заданию от 11 октября 2026 года, уточнено по ограничениям владельца. Сейчас цель — концепт с минималистичным интерфейсом и бюджетом $0. UI и логика разделены; платный backend, production и публичные desktop/mobile-релизы — будущие этапы.

## Рекомендуемый стек

Сохранить TypeScript, React, Vite и существующие компоненты MUI, обновив их представление через собственные токены. Основные референсы владельца — Zen Notes и Monkeytype, темы в духе Tokyo Night и минимализм чата. Этимологическое дерево — собственный SVG. Бесплатное демо оставить на существующем GitHub Pages, проверки — GitHub Actions. Electron сейчас используется локально при разработке.

Собственный API сейчас не является условием создания концепта. Грамматический UX сначала можно проверить на явно обозначенных, вручную сверенных примерах; затем исследовать бесплатный локальный parser. После появления бюджета при необходимости подключить cloud gateway на Cloudflare. Большую NLP-модель на Worker заранее не размещаем: требования проверяются отдельно.

## Где размещать приложение

Решение для текущего этапа: сохранить бесплатный GitHub Pages и не подключать платные тарифы, расходуемые кредиты или trial как обязательную инфраструктуру. Покупка домена не требуется. Таблица ниже — справка для будущего этапа, а не план расходов демо. Тарифы проверены 11 октября 2026 года; стоимость NLP API, домена, подписи Electron и налогов считается отдельно.

| Вариант | Стоимость и условия | Роль для Lingua |
|---|---|---|
| Текущий GitHub Pages | Статический публичный сайт, без собственного серверного runtime; ограничения на использование для коммерческого SaaS | Сохранить текущую демонстрацию до готовности нового хостинга |
| Cloudflare Workers Static Assets | Обычная раздача статических assets бесплатна; динамический код считается отдельно | Рекомендуемое размещение Vite web/dist с API по тому же origin |
| Cloudflare Worker API | Free: 100 тысяч запросов в день, 10 ms CPU на вызов; Paid от $5 в месяц с включёнными объёмами и доплатой за превышение | Небольшой gateway к выбранному NLP/переводческому провайдеру |
| Vercel | Hobby $0 для личного некоммерческого использования; Pro от $20 в месяц и возможные дополнительные расходы | Хорошая альтернатива, если удобство платформы важнее минимального бюджета; переход на Next.js не требуется |
| Railway | Hobby от $5 минимального месячного usage, потребление сверх включённого объёма оплачивается | Кандидат для контейнера собственного NLP, если потребуется тяжёлый runtime |

Сейчас миграция хостинга не нужна. Cloudflare — возможный следующий шаг, если понадобятся превью или API и бесплатные ограничения будут подходить. Платный переход обсуждается только после готового полезного сценария и появления средств.

При будущем выборе Cloudflare предпочесть один проект Workers Static Assets для веба и небольшого API. Статические файлы обслуживаются без запуска Worker, API-маршруты запускают обработчик. SPA fallback только для экранов: неизвестный `/api/*` возвращает JSON 404, не index.html.

До выбора имени использовать домен платформы. При собственном домене веб и `/api` остаются на одном origin. Текущую GitHub Pages ссылку переключать только после проверки пермалинков и коллекции: localStorage привязан к origin, поэтому нужен ручной экспорт/импорт для переноса старых данных.

Источники: [Cloudflare Static Assets billing](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/), [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/), [Vercel pricing](https://vercel.com/pricing), [Vercel Hobby](https://vercel.com/docs/plans/hobby), [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits), [Railway pricing](https://railway.com/pricing).

## Как разделить дизайн и логику

Направление зависимости: UI использует приложение и контракты; предметная логика не знает о React, MUI, DOM, Electron или Cloudflare.

```text
React views + MUI theme + SVG
            ↓
Controllers / hooks / view models
            ↓
Application use cases + typed ports
            ↓
Pure linguistic models and transformations

Platform adapters implement ports:
web fetch · Electron IPC/local parser · API provider gateway · local storage
```

В чистой логике находятся модели токенов/связей/этимологии, проверки графа, нормализация идентификаторов и преобразования результатов. Прикладной слой организует получение данных, кэш, отмену, частичные результаты и вызовы адаптеров. Компоненты получают готовые состояния и обработчики действий. Ошибки и загрузка не вычисляются через стили или типы MUI.

Предлагаемые изменения внутри существующей структуры, без обязательной миграции в монорепозиторий:

```text
src/shared/                 контракты без UI-зависимостей
src/core/domain/            чистые модели и преобразования
src/core/application/       сценарии и интерфейсы адаптеров
src/core/adapters/          браузеросовместимые словарь и HTTP
src/renderer/src/features/  sentence-analysis и word-origins
src/renderer/src/ui/        простые компоненты представления
src/renderer/src/theme/     палитра, типографика, размеры, motion
src/main/adapters/          Electron IPC и возможный локальный parser
api/                       Worker entry, validation, provider adapters
```

Переносить по одному сценарию, сохраняя прежние entrypoints. Сначала извлечь orchestration из `Translator.tsx` в controller/hook, затем отделить view. Не создавать интерфейс для каждого небольшого helper: порты нужны на границах внешних зависимостей — parser, словарь, перевод, хранилище.

SVG-дерево дополнительно разделить на три части: исторический граф, функция раскладки, визуальный компонент. Функция раскладки принимает измерения подписей и настройки геометрии, возвращает позиции/кривые. Она не выполняет fetch. Тема управляет цветом и оформлением, не решает, какие слова исторически родственны.

Критерий разделения: смена Tokyo Night на светлую или любую другую тему не меняет результат анализа; тот же результат можно показать текстом или деревом; parser можно заменить без переписывания компонентов.

## Современный редизайн

Уточнение сценария по интерактивному концепту: центр продукта — чтение и объяснение небольшого выбранного фрагмента. Перевод — раскрываемый дополнительный слой. Длинный документ хранится отдельно от анализа вхождения: `SourceDocument` содержит текст, `AnalysisSelection` — ID документа, UTF-16 диапазон и область разбора, `StudyNote` — неизменяемый снимок контекста и доступных результатов. Parser получает ограниченный контекст предложения; сохранённая заметка не меняется вслед за новым вводом.

Экспорт разделить на чистые сериализаторы Markdown/JSON и отдельный HTML/SVG renderer отчёта. Они принимают один снимок заметок и графа, не вызывают провайдера и не зависят от React, MUI или Electron. Схема JSON версионируется. Скачивание/копирование/печать относятся к платформенным адаптерам; это позволяет использовать один отчёт в вебе и desktop. Анимации работают в слое представления со стабильными ID узлов и не меняют лингвистические данные.

Основные референсы — Zen Notes и [Monkeytype](https://monkeytype.com/about). От них берём фокус на тексте, спокойный минимализм и выбираемые темы. Название Zen Notes относится к нескольким публичным приложениям; конкретную ссылку не подменяем случайным совпадением. Для первых макетов достаточно указанного владельцем направления.

Material UI уже установлен и может остаться технической основой доступных контролов. Внешний вид задаётся собственной системой токенов: неброские кнопки, почти плоские поверхности, минимум теней/контейнеров, тонкие разделители только где они помогают чтению. Большая постоянная AppBar и набор одинаковых Cards не становятся основой композиции.

Первый экран — рабочее пространство языка: поле предложения, команда Analyze, результат и переключение между Sentence structure и Word origins. В грамматике выбранное слово связано с исходным текстом и карточкой признаков. В этимологии большая часть площади отдана дереву, подробности открываются рядом. Не повторять повсюду тяжёлые рамки и карточки ради стандартного dashboard.

Сохранить English UI. Начальная тема прототипа — Tokyo Night; дополнительно Light и нейтральная Dark. Тема выбирается в небольшом меню с цветовым превью, выбор хранится локально без аккаунта; отдельный System режим учитывает тему ОС. Предпросмотр темы не сбрасывает текст, выбранное слово и масштаб дерева. Темы используют одни компоненты и схему токенов.

Роли цветов остаются стабильными: текст, вторичный текст, активное слово, общий предок, заимствование, ошибка и фокус. Конкретные оттенки меняются с темой и проверяются на контраст. Состояния дополнены линией, формой и текстом. Новое пожелание владельца уточняет ADR-008: Atlas можно сохранить как дополнительную тему, но он больше не обязательный внешний вид. Обновление архитектурного решения оформить при реализации.

Главная зона — читаемое предложение и ввод; панели подробностей открываются по выбору слова. История и коллекции доступны из компактной навигации, настройки — по запросу. Клавиатурные действия поддержаны, но функции остаются обнаружимыми через видимые controls. Фокус, ошибка и загрузка не становятся незаметными ради минимализма. Разбор и дерево сохраняют информацию; уменьшаем постоянный визуальный шум, а не доступные возможности.

Токены: semantic colors, surface levels, typography, spacing, density, focus, borders/radius и motion. MUI overrides и SVG/CSS читают согласованные значения, вместо локальных произвольных цветов в каждом компоненте. Для таблиц/признаков нужен компактный режим; для чтения текста — спокойный просторный режим.

Tailwind + Radix/shadcn возможны при необходимости радикально другого визуального языка. Сейчас переход потребует пересобрать формы, темы, фокус, модальные окна и другие работающие элементы. Это не решает отделение дизайна от логики само по себе. Не смешивать две полные библиотеки компонентов в одном сценарии.

До реализации подготовить два варианта композиции в направлении Zen Notes/Monkeytype: спокойное пространство чтения и более компактное пространство разбора. На выбранной композиции показать Tokyo Night и Light. Органичное дерево из blue-tree сохраняется отдельным визуальным акцентом. Проверить неизвестное слово, ошибку, неоднозначность и большое дерево; демо-разборы явно обозначены.

## Минимальный backend

Этот раздел относится к будущему подключению облака; сейчас backend не разворачиваем. Предлагается TypeScript API с небольшим router, например Hono. Его работа: валидировать запрос, применить ограничения, вызвать конкретный провайдер, проверить ответ и вернуть общий `SentenceAnalysis`. Предметные типы общие с клиентом, runtime-схема валидирует недоверенные JSON-ответы.

Минимальные маршруты:

| Маршрут | Назначение |
|---|---|
| `GET /api/v1/health` | Версия API/build, состояние самого gateway без платного NLP-вызова |
| `GET /api/v1/capabilities` | Поддерживаемые языки/режимы, лимиты ввода, версия контракта |
| `POST /api/v1/analyze` | Текст, язык и режим → токены, признаки, зависимости, статусы и metadata движка |
| `POST /api/v1/translate` | Только если требуется серверный платный перевод; иначе существующий адаптер сохраняется |

Provider выбирается серверной конфигурацией из разрешённых вариантов. Пользователь не передаёт произвольный URL или стоимость модели. Семантические объяснения, если нужны, выделяются отдельным режимом/результатом и не подменяют зависимости.

Не добавлять PostgreSQL, аккаунты, Redis, очередь и Kubernetes для первого gateway. Пользовательские коллекции остаются локальными. Технический счётчик квоты может требовать небольшого серверного хранилища; это отдельная задача, не база пользовательских предложений.

Перед публичным платным анализом нужны ограничение длины и размера body, rate limit, лимит расхода у провайдера, общий лимит бюджета и возможность отключить анализ. CORS полезен для браузера, но не защищает API от внешних скриптов. Секрет, встроенный в Electron/веб, тоже не становится защитой. Для закрытого пилота можно использовать выдаваемые сервером отзывные приглашения без полного аккаунта; они не должны быть общим ключом в сборке.

Строгая общая квота должна учитывать все экземпляры API через согласованный атомарный счётчик либо лимит провайдера. Переменная в памяти serverless-процесса не гарантирует глобального ограничения. Проверить поведение при параллельных запросах и недоступности счётчика; при необходимости платный вызов запрещается до подтверждения квоты.

Не логировать исходные предложения, ответы с текстом, URL с текстом или секреты. Эксплуатационные события — версия, код ошибки и длительность с ограниченным хранением; это пересмотр текущего обещания отсутствия любых дополнительных данных. Политика API отдельно объясняет, какой сервис получает предложение. Не обещать отсутствие хранения у внешнего провайдера без проверки его условий.

Этимология первоначально остаётся через существующий Wiktionary adapter. Серверный словарный proxy добавляется только при измеренной необходимости; throttling после этого должен учитывать общий upstream-поток, а не только один браузер. Общий кэш пользовательских предложений на старте не нужен.

Если выбран собственный тяжёлый parser, его можно запускать локально в Electron или отдельным контейнером, например FastAPI на Railway. Worker тогда gateway, а не место вычисления модели. У обычного Workers isolate 128 MB памяти; пригодность конкретного parser определяется измерениями и поддержкой библиотек. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/).

При появлении API оформить новое решение, продолжающее последовательность ADR и ссылающееся на ADR-009. Старую запись об отсутствии backend сохранить как историю. Доступность grammar engine отображается для каждой поверхности; не обещать одинаковые возможности при desktop-only модели.

## CI и CD

CI отвечает на вопрос «корректно ли изменение», CD публикует прошедшую проверку версию. В текущем `deploy-web.yml` деплой зависит лишь от собственной web-сборки и не ждёт общий CI. Это главный пробел, который стоит исправить первым.

Цепочка для одной версии:

```text
PR → types + tests + all builds → preview для доверенной ветки
                                      ↓ просмотр дизайна
merge main → тот же полный gate → проверенный artifact → production
tag vX.Y.Z → gate тега → installers → draft release → публикация
```

Предлагается один workflow проверки и публикации веба с jobs `verify → build → deploy`, либо reusable verify workflow с явным `needs`. Production разрешён только для защищённого main и успешных проверок того же SHA. Автоматический deploy со стороны хостинга, обходящий gate, отключается. Не использовать просто «последний зелёный CI» без привязки к коммиту.

Проверки: `npm ci`, typecheck, существующие тесты дерева, содержательные тесты токенов/контракта/графа, desktop/extension/web builds, сборка API при его появлении. Статический lint добавить при внедрении согласованной конфигурации, а не вызывать отсутствующую команду.

Локальный CI использует Node 22; GitHub main CI уже Node 24 и запускает тесты, в deploy/release пока Node 22. Выбрать один проверенный Node release для scripts, Docker и Actions, совместимый с TypeScript/Electron/tests. Нельзя считать эти среды одинаковыми до сверки.

Docker CI сейчас повторяет typecheck и builds. Сохранять обязательный контейнерный gate при изменениях Dockerfile/lockfile/build-config, при обычной UI-правке не дублировать весь pipeline без причины. Если будут path-фильтры, обязательный итоговый status должен корректно проходить для docs-only PR, не оставляя вечный pending.

`web/dist` после проверок упаковывается как artifact с SHA. Deploy использует именно его, не делает вторую независимую сборку. API bundle/config также привязаны к тому же коммиту. Артефакт trusted main не подменяется artifact из внешнего PR.

Для первого CI нужны детерминированные фикстуры: реальные платные API не вызываются на каждом PR. Минимальная UI-проверка проверяет целый сценарий с подставленным ответом. Скриншоты трёх контрольных деревьев помогают проверять редизайн; не блокировать релиз хрупкими snapshot-тестами каждого текста.

PR preview и production после merge относятся к разным SHA и получают разные артефакты. Повторно используется артефакт конкретного коммита между его staging и production. Чтобы это работало, окружения не должны требовать разных встроенных Vite-настроек: конфигурация API предпочтительно runtime, base и прямые переходы проверяются отдельно.

Preview — удобный следующий шаг после gate. Для собственного PR доступна отдельная preview-версия, без production-ключа NLP; внешние PR проверяются без deploy secrets. Не запускать чужой код через `pull_request_target` с привилегиями. URL публичного preview сам по себе не делает данные приватными.

Secrets хостинга/провайдера только в окружениях CI/runtime с ограниченными разрешениями. Для deploy используется отдельный минимальный token. Производственное окружение и preview имеют отдельные квоты. Pipeline останавливает устаревшие web-сборки, но не прерывает уже начавшуюся публикацию без причины.

После deploy выполнить короткую проверку: загрузка SPA/assets, version SHA, capabilities/health API, fixture mode. Проверка здоровья не расходует платную модель. При отказе вернуть предыдущую совместимую версию; UI/API контракт эволюционирует с поддержкой предыдущего клиента. Откат кода не восстанавливает автоматически изменения данных, если база появится позже.

Публичные Electron-релизы и mobile отложены. Существующий Electron остаётся средой локальной разработки. Когда desktop станет целью релиза, собирать установщики на тегах с проверками того же коммита и проверкой обязательных файлов. Подпись, notarization и автообновление — отдельные будущие задачи. Для mobile сейчас достаточно адаптивного веб-макета; нативную платформу заранее не выбирать.

## Порядок внедрения

1. Показать минималистичный концепт с Tokyo Night/Light, выбранным словом и красивым деревом на сверенных примерах.
2. Отделить controller от UI, ввести токены и сохранить понятный контракт результата для будущего parser.
3. Сверить git baseline и привязать существующий бесплатный Pages deploy к успешному CI того же SHA.
4. Подключать доступные бесплатные данные и исследовать локальный grammar engine; платные варианты сравнивать документально до появления бюджета.
5. Проверить, нравится ли автору законченный сценарий; собрать небольшую добровольную обратную связь по демо.
6. После подтверждения полезности и появления средств отдельно выбрать production backend, платные тарифы и desktop/mobile стратегию.

Готовность: тема меняется без изменения анализа, parser заменяется через адаптер, красный CI не публикует production, commit SHA проверяется после deploy, пользовательские тексты не попадают в логи, provider secrets отсутствуют в клиенте, стоимость облачных запросов ограничена.

Требуются новые предложенные ADR по разделению слоёв, хостингу/CI, redesign и API. Их номера выбираются после сверки полного актуального списка. Это дополнение не создаёт аккаунтов, не меняет production и не вводит платные подписки.
