# Uberlang долгосрочный план backend и Rust

18 октября 2026 года. Направление владельца — модернизация и оптимизация backend с перспективой переноса на Rust. Это план исследования и возможной миграции, а не решение немедленно переписать работающую систему. Реализация остаётся за владельцем; текущие задачи полезности продукта и качества интерфейса сохраняют приоритет.

## Архитектурное решение для планирования

Сохранять простейшую модульную систему, подходящую раннему продукту: один API с явными границами анализа, словаря и провайдеров; существующий отдельный NLP worker оправдан загрузкой модели и ограничением вычислений. Не вводить микросервисы, очередь, базу или Redis ради смены языка. Чёткие контракты и независимые тесты важнее одинакового языка во всех процессах.

Полная перепись на Rust — желаемое долгосрочное направление, а не доказанная необходимость. Сначала измерить задержки, память, эксплуатационные ограничения и стоимость сопровождения. Если преимущество не подтверждается, сохранить нынешний модуль или гибрид Rust API + Python NLP и обсудить это с владельцем. Называть гибрид «полностью Rust backend» нельзя.

## Что есть в репозитории сейчас

| Граница | Фактические компоненты | Значение для плана |
|---|---|---|
| Публичный web gateway | `api/analysis.mjs`, `lexicon.mjs`, `etymology.mjs`, `health.mjs`; `server/src/public-gateway.ts` | Same-origin проверки, размеры запросов, вызов внутреннего API, отмена; существующие Node/Vercel entrypoints |
| Внутренний API | `server/src/app.ts`, `schemas.ts`, `config.ts`, `resilience.ts`, `index.ts` | TypeScript/Fastify, авторизация, валидация, лимиты, readiness/drain; локальный Node/Docker и serverless-адаптер |
| Сборка языкового результата | `analysis.ts`, `live-analysis.ts`, `sentence-meaning.ts`; `src/data/reading-fixtures.mjs` | Prepared/live/unavailable слои, проверка дерева зависимостей и диапазонов; объяснение по грамматике, не полный семантический анализ |
| Словарь и история | `server/src/lexicon.ts`; `src/core/wiktionary.ts`; `src/shared/etymology.ts` | English Wiktionary, языковые разделы, типизированные отношения и ревизии; общий ограниченный кэш и планировщик сетевых запросов |
| Перевод | `src/core/providers.ts` и соседние адаптеры | Общий код также используется локальными Electron/extension; публичный gateway отключает перевод. Не переносить его молча вместе с сервером |
| NLP | `api/engine.py`, `engine/http_handler.py`, `engine/analyzer.py` | Приватный Python worker; `requirements.txt` фиксирует spaCy 3.8.7 и `en_core_web_sm` 3.8.0; загружаемая модель кэшируется, вычисление ограничено семафором |
| Проверки и сборка | `server/test/`, `engine/test_*`, `scripts/engine-benchmark.py`, Vite server/gateway configs, Dockerfile и CI | Существующие контракты, локальный cold/warm benchmark модели, сборки Node/Python. Это не замеры production-нагрузки |

Rust-кода backend в этом плане не добавляется. Browser-compatible `src/core/`, фронтенд, D3/Motion, клиентские экспорты и хранилища не являются объектом серверной переписи.

## Неподвижные контракты

Сохранить публичные `/api/analysis`, `/api/lexicon`, `/api/etymology`, health и совместимый внутренний `/v1` API; JSON-схемы, статусы ошибок, request/document identity и `[start,end)` в **UTF-16**, включая non-BMP и комбинируемые символы. Номера байтов не заменяют координаты текста.

Сохранять отдельные prepared/live/unavailable и meaning/grammar/etymology слои, модель и версию grammar, альтернативные значения/этимологии, источники и ревизии, `*`, пропущенные этапы, типы component/form-of/borrowed/inherited и CC BY-SA. Не расширять обещания языкового покрытия при смене реализации.

Origin/auth, ограничения размера/частоты/параллелизма, deadlines, отмена при disconnect, no-store и безопасные ошибки остаются проверяемыми инвариантами. Не переносить ключи в браузер и не записывать исходный текст, query, IP или credentials в логи. Смена runtime не мигрирует данные пользователей и не меняет домены или аккаунты.

## Нулевой этап и измерения

Использовать неперсональный фиксированный корпус и зафиксированные словарные ревизии. Сохранить коммит, окружение, модель, число запусков и разброс; результаты пока отсутствуют. Разделить cold start/import/model load, тёплый HTTP/JSON, валидацию, CPU словарного парсинга, сетевое ожидание и очередь, spaCy inference, cache hit/miss, RSS, артефакт сборки и поведение перегрузки. Измерять p50/p95, ошибки, отмену и фактическое число обращений к источнику.

Нынешний транспорт Wiktionary сериализует запросы с минимальным интервалом 150 ms (`src/core/wiktionary.ts`). Словарный guard допускает две операции и deadline 7000 ms; parser guard — две операции и 20000 ms (`server/src/app.ts`). Кэш статей — до 128 страниц / 2M символов, TTL один час (`server/src/lexicon.ts`); Python вычисляет по одному запросу на worker. Это ограничения реализации, **не доказанные узкие места**. Более старые ADR/описания могут отставать от кода.

До прототипа определить вместе с владельцем целевые улучшения и допустимый регресс: конкретный измеренный маршрут/метрика, воспроизводимость сверх шума, отсутствие контрактных/лингвистических регрессий и увеличение сложности, которое автор готов сопровождать. Бюджет остаётся $0; экономия и ускорение не предполагаются заранее. Локальный `scripts.engine-benchmark` даёт полезный исходный инструмент, но не hosted SLO и не оценку точности.

## Один ограниченный прототип

После отдельного разрешения на реализацию проверить **только read-only `/v1/etymology`**: Rust-адаптер HTTP/JSON, модуль извлечения поддержанных отношений и подставной адаптер словарных страниц с фиксированными ревизиями. Интерфейсы отделяют словарное чтение от преобразования данных; framework и сеть остаются на границе. Python/spaCy не переписывать, новые функции не добавлять и production-трафик не дублировать.

Сравнить с TypeScript на одинаковых входах, лимитах и аппаратной среде. Проверить отдельно время на локальных данных и end-to-end путь с разрешённым источником: быстрый CPU benchmark не доказывает ускорения чтения словаря. Если накладные расходы HTTP/парсинга малы относительно сети или модели, не продолжать полную перепись ради синтетического результата.

Проверить осуществимость сборки, binary/runtime/FFI, cold start, памяти, CI, деплоя и отката на существующем бесплатном размещении. Поддержка подходящего Rust runtime и необходимость платформенных адаптеров ещё требуют проверки; план не разрешает менять хостинг, тарифы, сервисы или ключи. Не выбирать web framework или набор crates до этой проверки.

## NLP и граница разумной миграции

На первом этапе оставить Python/spaCy за существующим приватным контрактом `Parse`, с pinned моделью и независимой проверкой ответа. Rust HTTP-слой сам по себе не заменяет parser, веса, морфологию и лингвистическую проверку качества. Не обещать дешёвого переноса NLP или снятия английского ограничения.

Замену NLP рассматривать отдельно, только если кандидат сохраняет качество на корпусе, координаты, labels/provenance, поведение неоднозначности, лимиты и лицензионные условия при приемлемых ресурсах. Если такой замены нет, обоснованно оставить Python; это честный компромисс архитектуры и отдельное решение владельца относительно цели «всё на Rust».

## Миграция и откат после положительного результата

1. Зафиксировать результаты и новый предложенный ADR с границами и критериями приёмки. Текущие ADR-012/013/014/016 не удалять и не считать заменёнными этим roadmap.
2. Прогнать differential/golden контрактные проверки TypeScript/Rust на публичных ревизиях: пустые/альтернативные этимологии, неопределённость, циклы, неподдержанные шаблоны, реконструкции, акценты, UTF-16 и атрибуция. Добавить отрицательные HTTP/auth/лимиты/отмена/drain проверки. Fake-провайдеры изолируют сеть; NLP остаётся в собственных тестах.
3. После разрешения на deployment выпустить один совместимый маршрут в изолированном preview. Старые API и Python продолжают работать; не отправлять личные тексты в новый процесс или shadow-запрос без отдельной авторизации.
4. Собирать ограниченные операционные показатели: request ID, шаблон маршрута, status/duration, перегрузка и агрегированные ресурсы. Сравнить задержку, ошибки, source-traffic, память, сложность и стоимость с baseline; не вводить продуктовую телеметрию ради миграции.
5. Сохранять предыдущий готовый артефакт и маршрутизацию для немедленного возврата к TypeScript. Триггеры отката — нарушения контракта/источников/приватности, регресс по согласованным метрикам, ошибки отмены, рост затрат или несовместимый старый клиент. Не делать fallback, который повторяет запросы бесконтрольно.
6. Переносить следующий модуль только после успешной проверки предыдущего и отдельного решения владельца. Старую реализацию удалять после проверки всех потребителей и понятного rollback; схема без серверной БД не требует придумывать миграцию данных. Если БД появится позже, её совместимость и откат — отдельный план.

В этой задаче разрешена только документация: нет Rust-реализации, установки зависимостей, новых сервисов, performance-заявлений, смены конфигурации, push или deployment.
